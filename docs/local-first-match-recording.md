# Local-first 경기 기록 전환 계획

상태: 구현 예정  
작업 브랜치: `local-first-match-recording`

## 배경

현재 경기 중 득점 입력은 사용자 탭마다 서버 액션을 호출한다. 득점 1건을 저장할 때 권한 확인, 경기/구간 조회, 득점 이벤트 삽입, 전체 득점 재집계, 경기 점수 갱신, 변경 로그 기록, 경로 재검증이 연속으로 수행된다. 편집 화면은 optimistic 이벤트와 추가 재조회로 지연을 가리며, 읽기 화면은 polling과 짧은 캐시를 사용한다.

이 구조는 여러 기기의 동시편집을 지원할 수 있지만, 경기장 네트워크 상태와 Vercel/Supabase 왕복 시간에 핵심 입력 UX가 의존한다.

## 제품 제약

첫 전환에서는 다음 제약을 명시적으로 채택한다.

- 경기당 활성 기록 기기는 한 대다.
- 경기 진행 중 해당 기기의 로컬 세션이 유일한 편집 원본이다.
- 다른 기기는 조회만 가능하다.
- 경기 종료 시 전체 이벤트 묶음을 서버에 동기화한다.
- 서버 동기화 실패는 경기 중 기록에 영향을 주지 않는다.
- 실시간 관전자 갱신은 핵심 기록과 분리된 선택 기능으로 둔다.

## 목표

- 득점, 득점 취소 및 기본 경기 이벤트 입력을 네트워크 없이 즉시 처리
- 새로고침이나 브라우저 재실행 후에도 진행 중 경기 복구
- 종료 동기화의 재시도와 중복 제출 안전성 보장
- 기존 리그 설정, 로스터, 일정, 완료 경기 통계 기능 재사용
- 한 단계씩 전환하여 기존 서버 중심 기록 기능을 fallback으로 유지

## 비목표

첫 버전에서는 다음을 지원하지 않는다.

- 여러 기록자의 실시간 동시편집
- 이벤트 단위 실시간 서버 저장
- 복잡한 충돌 병합
- 모든 관리자 기능의 오프라인 지원
- 관전자 화면의 초 단위 실시간 보장

## 데이터 흐름

1. 경기 입장 시 서버에서 경기, 팀, 로스터, 구간 정보를 다운로드한다.
2. 편집 시작 시 로컬 경기 세션을 생성한다.
3. 경기 중 이벤트는 메모리 상태에 즉시 적용하고 IndexedDB에 영속화한다.
4. UI는 서버 재조회 없이 로컬 세션에서 점수와 타임라인을 계산한다.
5. 경기 종료 시 세션 스냅샷과 이벤트 로그를 하나의 동기화 요청으로 제출한다.
6. 서버는 `sessionId`와 이벤트 `id`를 기준으로 중복을 제거하고 트랜잭션으로 확정한다.
7. 성공 응답을 받은 뒤 로컬 세션을 `synced`로 표시한다.

## 로컬 세션 계약

```ts
type LocalMatchSession = {
  schemaVersion: 1
  sessionId: string
  matchId: string
  baseRevision: string | null
  deviceId: string
  status: 'recording' | 'pending_sync' | 'synced'
  startedAt: string
  endedAt: string | null
  updatedAt: string
  events: LocalMatchEvent[]
}

type LocalMatchEvent = {
  id: string
  sequence: number
  type:
    | 'period_started'
    | 'period_ended'
    | 'goal_added'
    | 'goal_removed'
    | 'goal_updated'
    | 'substitution_added'
  occurredAt: string
  periodSequence: number | null
  payload: Record<string, unknown>
}
```

점수는 별도로 증분 저장하지 않고 유효한 `goal_added`와 `goal_removed` 이벤트를 재생하여 계산한다. 파생 상태를 줄여 점수와 득점 이벤트 불일치 문제를 방지한다.

## 동기화 API 계약

`POST /api/matches/:matchId/sync`

요청:

```json
{
  "schemaVersion": 1,
  "sessionId": "match-id.device-id.random",
  "baseRevision": "server-revision-at-start",
  "startedAt": "2026-08-13T05:00:00.000Z",
  "endedAt": "2026-08-13T06:00:00.000Z",
  "events": []
}
```

응답:

```json
{
  "status": "synced",
  "matchId": "match-id",
  "sessionId": "match-id.device-id.random",
  "acceptedEventIds": [],
  "serverRevision": "new-revision"
}
```

동일한 `sessionId`와 이벤트 ID를 다시 제출해도 결과가 달라지지 않아야 한다. 네트워크 타임아웃 이후 사용자가 안전하게 다시 시도할 수 있어야 한다.

## 저장소 선택

브라우저 저장소는 IndexedDB를 사용한다.

- 이벤트가 늘어도 동기 API인 localStorage보다 안전하다.
- 구조화된 세션과 인덱스를 저장할 수 있다.
- 이후 이미지나 첨부 데이터가 생겨도 확장 가능하다.

외부 상태 라이브러리는 첫 단계에 추가하지 않는다. 작은 IndexedDB 어댑터와 React 훅으로 시작하고, 복잡도가 실제로 증가할 때만 라이브러리를 검토한다.

## 전환 단계

### 1단계: 측정과 경계 분리

- 현재 득점 저장 왕복 시간과 실패를 기록
- 서버 액션과 화면 컴포넌트 사이에 경기 기록 인터페이스 정의
- 기존 서버 기록기를 `ServerMatchRecorder`로 감싼다
- 사용자 동작은 변경하지 않는다

완료 조건: 기존 기능이 동일하게 동작하며 저장 방식 교체 지점이 하나로 모인다.

### 2단계: 로컬 득점 기록

- IndexedDB 세션 저장소 구현
- 득점 추가, 취소와 수정 이벤트 구현
- 로컬 이벤트에서 점수와 타임라인 계산
- 새로고침 복구 및 미동기화 표시
- 기능 플래그로 관리자 또는 샘플 채널에서만 활성화

완료 조건: 네트워크를 끈 상태에서 경기 시작 후 득점 기록과 새로고침 복구가 가능하다.

### 3단계: 종료 동기화

- 원자적 sync API 구현
- 세션 및 이벤트 ID 기반 멱등성 보장
- 실패 시 로컬 보존과 수동 재시도 제공
- 서버 반영 결과와 로컬 결과 검증

완료 조건: 동일 세션을 반복 제출해도 득점이 중복되지 않으며, 실패 후 재시도가 가능하다.

### 4단계: 구간과 교체 기록 전환

- 구간 시작/종료
- 선발 명단
- 선수 교체
- 득점자·어시스트 사후 보정

완료 조건: 한 경기의 핵심 운영이 서버 왕복 없이 가능하다.

### 5단계: 선택적 관전자 스냅샷

- 기록 세션과 분리된 저우선순위 스냅샷 업로드
- 실패 시 조용히 건너뛰고 다음 주기에 재시도
- 관전자 화면은 마지막 성공 스냅샷과 갱신 시각 표시

완료 조건: 관전자 기능 장애가 기록 기기 입력에 영향을 주지 않는다.

## 기존 코드 처리

- `GoalAddActions.tsx`: 입력 UI는 유지하고 recorder 인터페이스에 이벤트 전달
- `LiveScoreboard.tsx`: 편집 모드에서는 로컬 파생 상태 사용, 읽기 모드는 기존 서버 조회 유지
- `page.tsx`: 서버 액션 직접 바인딩을 recorder 경계로 이동
- `addGoalDetailed`: 전환 중 fallback으로 유지, 최종적으로 종료 동기화 내부 로직으로 재사용 또는 제거
- `docs/cache-policy.md`: 라이브 편집 화면의 no-store 의존을 제거한 뒤 정책 갱신

## 성능 검증

각 단계에서 다음을 측정한다.

- 득점 버튼 탭부터 점수 표시까지의 시간
- 이벤트 영속화 완료 시간
- 경기 화면 초기 로드 시간
- 30분 경기 중 네트워크 요청 수
- 새로고침 후 세션 복구 성공률
- 종료 동기화 시간과 실패율
- 중복 제출 시 데이터 일관성

목표:

- 득점 표시 p95 50ms 이하
- 로컬 영속화 p95 100ms 이하
- 경기 중 필수 네트워크 요청 0건
- 새로고침 복구 성공률 100%
- 동일 세션 재동기화 시 중복 이벤트 0건

## 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 기록 기기 분실 또는 브라우저 데이터 삭제 | 경기 중 선택적 백업 스냅샷을 후속 제공 |
| 두 기기가 동시에 기록 시작 | 활성 기록기 lease 또는 명시적 인계 기능을 후속 구현 |
| 서버 데이터가 경기 중 수정됨 | 시작 시 `baseRevision` 저장, 종료 시 충돌을 사용자에게 표시 |
| 브라우저 저장 용량 및 사생활 보호 모드 | 시작 전 저장소 쓰기 테스트와 경고 |
| 기존 데이터 모델과 이벤트 계약 차이 | sync API에서 변환하고 DB 스키마는 초기에는 최대한 유지 |

## 첫 구현 작업

1. 경기 기록 인터페이스와 이벤트 타입 추가
2. 기존 서버 기록기를 인터페이스 뒤로 이동
3. 저장 시간 측정 추가
4. IndexedDB 세션 저장소와 단위 테스트 추가
5. 샘플 채널에서 로컬 득점 기능 플래그 활성화
